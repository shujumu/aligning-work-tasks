# Aligning Work Tasks 设计规格

日期：2026-07-28

## 1. 目标

创建一个可安装的 Codex Skill，将模糊、冲突或不完整的职场任务转成可执行、可验证、可持续跟踪的任务交接。Skill 同时支持任务下达者、执行者和验收者，覆盖任务接收、范围澄清、步骤拆分、证据检查、状态判定、任务表更新和向上汇报。

项目以 GitHub 仓库形式交付，包含中文 README、跨行业研究、可复用 Skill 和公开的评测场景。远端仓库默认设为私有；未明确开放复用前不附开源许可证。

## 2. 非目标

- 不直接登录 ERP、社交媒体、财务、医疗或生产系统。
- 不自动发布内容、修改生产数据、付款、删除数据或对外发送消息。
- 不替代所在组织的审批、授权、合规和专业判断。
- 不把所有任务扩展成复杂项目；信息充分且风险低时直接执行。
- 没有文件或可写工具时，不声称已经更新任务表，只输出可复制的增量记录。

## 3. 核心用户场景

1. 执行者收到零散、模糊或相互冲突的上级消息，需要确认做什么、做到什么程度以及如何证明完成。
2. 管理者准备下达任务，需要检查目标、范围、截止时间、责任、权限和验收标准是否完整。
3. 任务执行中出现范围变化、阻塞或部分完成，需要重述变化并维护统一状态。
4. 验收者收到截图、表格、日志或结果说明，需要判断证据是否支持结论。
5. 跨班次、跨团队或跨岗位交接时，需要避免遗漏背景、已做操作、当前状态和下一步。

## 4. 通用工作流

1. 接收原始任务、任务表、沟通记录和用户提供的附件。
2. 识别并避免回显密码、令牌、客户隐私、银行信息和其他无关敏感数据。
3. 按任务编号、项目编号或可区分的工作项建立清单。
4. 分离明确事实、待确认项、冲突信息和暂定假设。
5. 建立任务契约：目标、交付物、范围、排除项、事实来源、环境、权限、责任人、期限、优先级、验收标准和所需证据。
6. 选择执行门禁：
   - 信息充分且低风险：直接生成最小执行步骤。
   - 信息不全但工作可逆：明确假设，先做不会造成外部影响的准备。
   - 信息不全且操作不可逆或高风险：提出最多三个最高价值问题，暂停危险操作。
7. 为每个工作项生成 Markdown 可勾选步骤，步骤必须具体、可观察、可验收。
8. 执行者返回证据后，检查证据是否同时覆盖身份、条件、操作、结果和验收标准。
9. 使用明确状态口径分类，列出不支持结论的具体缺口。
10. 用户提供任务表或可写工具时更新原记录；否则输出字段级增量。
11. 生成可直接提交给上级的事实型结果摘要，同时保留阻塞项、风险和下一步。

## 5. 状态口径

问题复测默认使用：

- 已恢复：约定范围全部通过，证据充分。
- 仍存在：在约定条件下复现，证据充分。
- 部分恢复：范围内存在通过与失败项，必须分别列明。
- 无法验证：缺少权限、数据、环境、条件或证据；不得等同于仍存在。

普通任务映射为：已完成、未完成或仍存在、部分完成、无法验收。Skill 根据任务语境选择标签，但不得改变判定逻辑。

## 6. 证据规则

证据充分性检查包含：

- 身份：能够定位任务、项目、对象或记录编号。
- 条件：能够确认环境、版本、时间、筛选条件或发布渠道。
- 操作：说明执行过的关键步骤，不依赖无法复核的口头结论。
- 结果：显示实际结果，而不只有操作前条件。
- 验收：结果能与预先约定的判断标准比较。
- 安全：截图和附件已遮挡与证明无关的秘密、账号和隐私。

使用图片时，优先上传“条件图 + 结果图”的成对证据。README 不鼓励无差别堆图，而是指导用户提供清晰、有编号、可追溯且已脱敏的最小证据集。

## 7. 行业适配

Skill 仅保留通用核心。`references/domain-lenses.md` 按需提供以下行业补充字段：

- ERP 实施：产品、环境、项目编号、账套或组织、模块、补丁版本、查询条件和回归结果。
- 新媒体运营：目标、受众、平台、账号、素材版本、文案事实、授权、发布时间、审批人和指标口径。
- 软件研发与测试：代码库、版本、环境、复现步骤、期望与实际结果、日志、测试和发布范围。
- 销售：客户、阶段、需求、报价权限、负责人、承诺、下一动作和 CRM 证据。
- 财务：主体、期间、账套、科目、数据源、差异阈值、复核和审计证据。
- 客服：工单、客户诉求、身份核验、已做操作、政策依据、升级原因和 SLA。
- 工程施工：图纸版本、位置、专业、现场条件、RFI、影响、批准和照片。
- 医疗交接：使用 SBAR/ISBAR 思路组织当前情况、背景、判断和建议，同时强化隐私与人工确认。
- 人力资源：岗位、编制、硬性条件、筛选标准、面试阶段、审批和候选人隐私。
- 采购与法务：对象、版本、条款、预算或授权、风险口径、审批链和来源文件。

## 8. 安全与权限

- 不要求用户提供密码、令牌、验证码或完整生产地址。
- 发现凭证时不回显，并提示撤销或轮换已暴露凭证。
- 生产修改、正式发布、付款、删除、合同承诺和外部发送必须获得明确授权。
- “没有回复”不得自动解释为批准，除非用户提供了已生效的书面默认批准规则。
- 医疗、财务、法律和人事结论必须保留专业人员复核。
- 对图片执行内容相关性和敏感信息检查；不把无关截图存入输出。

## 9. Skill 输出形式

根据用户需要生成一种或多种输出：

1. 对齐消息：可以直接发给上级、下级或协作方的简洁确认文本。
2. 任务契约：结构化的目标、范围、排除项、责任、期限和验收标准。
3. 执行清单：按工作项划分的 Markdown 复选框步骤。
4. 证据检查：充分、存在缺口或相互矛盾，并列出缺口。
5. 状态增量：可复制到 Excel、表格或任务系统的字段更新。
6. 向上汇报：完成情况、证据、阻塞、风险和下一步。

输出默认简洁。只有任务复杂、用户要求完整报告或存在高风险时才展开全部结构。

## 11. README 使用指南

README 包含：

- Skill 能解决和不能解决的问题。
- 本地安装与显式调用方式。
- 首次使用示例和三种常用提示词。
- 如何提供原始任务、沟通记录、现有任务表和项目编号。
- 如何在同一对话中持续报告进度与变更。
- 如何上传条件图和结果图、编号图片、裁剪无关内容并脱敏。
- 如何要求 Skill 生成对齐消息、任务清单、证据检查、表格增量和上级汇报。
- 为什么不能上传密码、客户隐私和未授权生产资料。
- 为什么外部发布、生产修改等动作仍需人工审批。

## 12. 测试策略

按 RED-GREEN-REFACTOR 测试：

- ERP 模糊复测任务：检查项目、环境、范围、证据和四状态分类。
- 新媒体紧急发布：检查素材版本、价格、授权和发布审批，禁止把沉默当授权。
- 清晰简单任务：检查 Skill 不过度追问或制造表格负担。
- 需求中途变化：检查差异、影响和重新确认内容。
- 证据不足：检查条件图与结果图缺失时不得判定完成。
- 包含密码和隐私：检查不回显并给出凭证处置建议。
- 无可写文件：检查只输出增量，不声称已更新。

当前无 Skill 基线已经暴露三类问题：模型可能自行创造授权规则、证据和状态口径不一致、以及在缺少持久化工具时暗示已完成更新。最小 Skill 必须直接约束这些失败。

## 13. 验证与交付

- 使用官方 `init_skill.py` 初始化 Skill。
- 使用 `quick_validate.py` 验证名称和 YAML frontmatter。
- 检查 `agents/openai.yaml` 与 Skill 内容一致。
- 对相同场景进行带 Skill 前向测试并记录结果。
- 扫描 TODO、TBD、占位符、内部客户信息和潜在凭证。
- 初始化本地 Git 仓库并提交通过验证的文件。
- 本地完成后尝试创建私有 GitHub 仓库；当前环境没有 GitHub CLI，因此若没有其他已认证集成，远端发布会作为唯一需要用户完成认证的步骤明确交接。

## 14. 成功标准

- 模糊任务能够形成可执行、可验证的最小任务契约。
- 高风险缺口能够阻止越权执行，低风险清晰任务不会被过度复杂化。
- 证据不足时不会输出“已完成”或“已恢复”。
- 四种状态互斥且每项结论可追溯到证据。
- README 能让新用户独立安装并完成一次任务对齐。
- Skill 通过官方验证和至少六类评测场景。
- 仓库中不包含真实客户信息、账号密码或未脱敏业务数据。
