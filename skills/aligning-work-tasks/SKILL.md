# 任务对齐

## 核心原则

把模糊请求收敛为最小任务契约，再决定能否执行。保护敏感信息，保留不确定性，以证据支撑状态和汇报。

## 1. 整理输入

- 不索取或回显密码、令牌等凭证；对个人信息、客户数据和内部地址做脱敏，只保留完成任务所需的最小信息。若凭证可能已经暴露，提示负责人通过授权渠道撤销或轮换；未经授权不要自行轮换。
- 分开记录：
  - **事实**：来源明确、可直接核对的信息。
  - **缺口**：执行或验收所必需但尚未提供的信息。
  - **冲突**：不同来源、版本、口径或指令之间的不一致。
  - **假设**：为继续准备而暂用的判断；标明待确认，不把它写成事实。
- 只追问会改变范围、权限、风险、执行方式或验收结论的问题。面对清晰、低风险、可逆的任务，直接执行，不要为填满模板而过度追问。
- 仅当领域字段会实质影响澄清或验收时，加载 [references/domain-lenses.md](references/domain-lenses.md)；通用任务不要加载。

## 2. 建立最小任务契约

至少对齐以下内容；从可靠上下文可确定的内容直接填入，仅把真正阻塞项列为问题：

| 字段 | 要求 |
| --- | --- |
| 目标 | 说明要改变、核验或交付什么 |
| 范围 | 列出项目、事项、时间段及明确不包含项 |
| 对象与环境 | 给出对象标识、系统、环境、版本或数据口径 |
| 输入 | 标明来源、文件版本、负责人和必要依赖 |
| 权限 | 区分只读核验、内部修改、生产修改、外部发布或审批 |
| 时限与优先级 | 给出截止时间、顺序和升级点 |
| 交付 | 指定格式、位置、接收人及是否需要真实更新 |
| 验收 | 定义完成标准、状态口径和所需证据 |

## 3. 设置执行门禁

| 门禁 | 使用条件 | 行动 |
| --- | --- | --- |
| **可直接执行** | 目标和范围清楚；权限明确；低风险、可逆；输入与验收足够 | 直接执行并留证，不额外等待确认 |
| **准备后确认** | 可安全完成只读查询、草稿、清单、脚本或表格增量，但关键口径或有副作用的动作仍待确认 | 先完成无副作用的准备，把待确认点集中提交；确认前不触发副作用 |
| **必须先确认** | 关键对象、范围、环境、权限或验收缺失/冲突，或行动不可逆、影响外部主体或高风险系统 | 停止相关执行，只说明阻塞项、风险和所需授权 |

沉默不等于授权。生产修改、外部发布或发送、删除、付款、权限变更、法律承诺及敏感数据处理等高风险行为，必须取得范围明确的显式授权；“尽快处理”或“领导没回复”不能替代授权。

## 4. 生成步骤并收集证据

- 按项目或事项分配稳定编号，如 `P01-I01`；为每个编号生成 Markdown 可勾选步骤。
- 在步骤中写明对象、输入/条件、操作、预期结果、证据和验收标准；只有实际执行且取得证据后才勾选。

```markdown
- [ ] P01-I01 确认对象与查询条件
- [ ] P01-I01 执行获授权的查询或操作
- [ ] P01-I01 保存证据并判定四态结果
- [ ] P01-I01 形成实际更新记录或待应用增量
```

为每项保留五类证据：

| 证据 | 回答的问题 |
| --- | --- |
| **身份** | 核验的是哪个项目、事项、记录、文件或版本？ |
| **条件** | 使用了什么环境、时间范围、过滤条件和前置状态？ |
| **操作** | 实际执行了什么，由谁、何时、通过什么工具执行？ |
| **结果** | 系统、文件或现场返回了什么可复查结果？ |
| **验收** | 哪条标准证明结论成立，谁有权接受？ |

截图需同时服务于证据目的并完成脱敏。查询核验优先成对保留“查询条件图 + 结果图”，避免只有结果而无法复现口径。

## 5. 判定状态并更新载体

每项只选择一种互斥状态，不把证据不足压缩成二元结论。保持同一判定逻辑，并按语境选择标签：

| 判定逻辑 | 问题复测 | 普通任务 |
| --- | --- | --- |
| 全部验收标准满足 | **已恢复** | **已完成** |
| 明确不满足验收标准 | **仍存在** | **未完成** |
| 仅部分范围或验收项通过 | **部分恢复** | **部分完成** |
| 身份、条件、权限、工具、数据或证据不足 | **无法验证** | **无法验收** |

对部分状态列出未通过项；对无法验证或无法验收列出具体缺失项和下一步。

只有工具能力和授权都允许时，才真实更新文件、任务表或外部系统，并记录载体、对象、字段、时间和证据。工具不可写、权限不足或用户只要求建议时，只输出标记为“待应用”的增量；不得声称“已更新”“已保存”或“已发布”。

```markdown
| 项目/事项 | 字段 | 原值 | 待应用值 | 依据 |
| --- | --- | --- | --- | --- |
```

## 6. 向上汇报

按“结论先行、证据随后、风险透明”汇报：

1. 写明核验/执行时点、范围和总体结论。
2. 按项目或事项编号列出四态、关键证据和验收口径。
3. 区分已真实更新与待应用增量，给出载体或路径。
4. 列出例外、风险、阻塞项、责任人、下一步和期望确认时间。
5. 不把假设包装为事实，不用工作量替代结果，不隐藏无法验证项。

## 端到端示例

**模糊消息**：“把上周那批问题核一下，修好的和没修好的分开，表更新后给我汇报。”

**三个阻塞问题**：

1. 请确认项目编号和问题清单，避免核验错对象。
2. 请确认环境、查询截止时点及日期/状态过滤口径。
3. 本次仅做只读核验，还是也授权发现问题后修改生产数据？

确认得到“`P01`、`P02` 两个项目；正式环境只读；截至 2026-07-27 18:00；仅核验”后，先形成项目清单。执行者完成只读查询并返回实际证据：`P01-I01` 在约定条件下显示成功，`P02-I01` 最近一次同步仍报错；核对条件图、结果图与验收标准后，才勾选步骤并判定状态：

```markdown
项目清单
- P01-I01：核验回单状态，期望状态为“成功”
- P02-I01：核验同步状态，期望最近一次同步无错误

执行清单
- [x] P01-I01 保存查询条件图 `P01-I01-condition.png`
- [x] P01-I01 保存结果图 `P01-I01-result.png`，判定“已恢复”
- [x] P02-I01 保存查询条件图 `P02-I01-condition.png`
- [x] P02-I01 保存结果图 `P02-I01-result.png`，判定“仍存在”
```

若工具没有表格写权限，只输出增量：

```markdown
待应用表格增量
| 项目/事项 | 待应用状态 | 查询条件图 | 结果图 | 备注 |
| --- | --- | --- | --- | --- |
| P01-I01 | 已恢复 | P01-I01-condition.png | P01-I01-result.png | 满足验收条件 |
| P02-I01 | 仍存在 | P02-I01-condition.png | P02-I01-result.png | 最近一次同步仍报错 |
```

**向上汇报**：“截至 2026-07-27 18:00，已按确认口径只读核验 2 项：`P01-I01` 已恢复，`P02-I01` 仍存在；每项均保留查询条件图和结果图。当前工具无表格写权限，未声称已更新，已附待应用增量。`P02-I01` 需由系统负责人确认修复授权与处理时限。”
